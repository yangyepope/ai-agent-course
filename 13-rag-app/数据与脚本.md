# 一、新增的文件

```
13-rag-app/
├── data/documents.json          语料：91 条 chunk，两个租户
├── app/                         被 import 的模块
│   ├── index_manager.py         mapping 定义 + 建/删/计数
│   └── document_service.py      读文件 → 批量向量化 → bulk 写入
└── scripts/                     命令行入口，跑完就退
    ├── init_index.py            建索引
    ├── index_documents.py       灌数据
    └── smoke_test.py            检索链路冒烟测试
```

分成两个目录的理由：`app/` 里的东西是**被 import 的**（服务启动时加载），
`scripts/` 里的是**手动执行的**（跑一次就结束）。
前者属于在线链路，后者属于离线准备，将来拆开部署时边界就在这。

> 注意用 `python -m scripts.xxx` 而不是 `python scripts/xxx.py`。
> 后者会把 `scripts/` 而不是项目根目录放进 `sys.path`，
> 于是 `from app.config import ...` 直接 ModuleNotFoundError。

# 二、跑起来

所有命令都在 `13-rag-app/` 目录下执行（路径是相对的）。

```bash
cd /opt/ai-agent-course/13-rag-app

python -m scripts.init_index          # 建索引
python -m scripts.index_documents     # 灌数据（91 条，约 3 秒）
python -m scripts.smoke_test          # 冒烟测试，不花 LLM 的钱
python -m scripts.smoke_test --llm    # 连生成一起跑

uvicorn main:app --reload         # 起服务
```

改了 mapping 或换了 Embedding 模型之后：

```bash
python -m scripts.init_index --recreate   # 先删再建，数据一起删
python -m scripts.index_documents         # 重新灌
```

# 三、索引用的是 rag_app_chunks，不是 rag_chunks

`.env` 原来写的是 `ES_INDEX=rag_chunks` —— 那是 **12 课的索引**，
里面只有 4 条数据。13 课灌 91 条进去会把 12 课冲掉，所以改成了独立索引：

```
rag_chunks       ← 12-elasticsearch-rag， 4 条
rag_app_chunks   ← 13-rag-app，          91 条
```

两个索引并存，互不影响。

# 四、数据构成

91 条，两个租户：

```
tenant-001  78 条   技术知识库
  redis          28   redis-guide.pdf(23) + redis-cluster.pdf(5)
  mysql          15   mysql-index.pdf(8) + mysql-transaction.pdf(7)
  java           15   java-gc.pdf(8) + java-concurrent.pdf(7)
  elasticsearch   8   es-guide.pdf
  kafka           7   kafka-guide.pdf
  docker          3   docker-guide.pdf
  nginx           2   nginx-guide.pdf

tenant-002  13 条   企业行政制度（换个领域，用来验证隔离）
  finance         5   finance-policy.pdf
  hr              5   hr-handbook.pdf
  it              3   office-it.pdf
```

正文长度 41~162 字，平均 67 字。

**为什么要凑到 91 条**：`RAGService.CANDIDATE_SIZE = 10`，
只有语料够多，「召回 10 条 → 精排挑 3 条」才有意义。
原来索引里只有 4 条，精排几乎无事可做。

**为什么故意留了歧义词**：
```
「内存」  → Redis 内存 / Java 堆内存 / ThreadLocal 内存泄漏
「日志」  → AOF / binlog / GC 日志 / Kafka 日志压缩
「分片」  → Redis Cluster / Elasticsearch
「隔离」  → 事务隔离级别 / 租户隔离
```
这些词能让 BM25 单独跑时出现误命中，混合检索的价值才看得出来。

# 五、冒烟测试测了什么

9 条 query，每条都打印「召回名次」和「精排名次」的对照：

| 租户 | query | 验证点 |
|---|---|---|
| 001 | `maxmemory-policy` | 专有名词，BM25 该稳稳命中 |
| 001 | `Redis内存满了怎么淘汰` | 字面不含关键词，靠向量 |
| 001 | `缓存里的数据同时失效导致数据库被打挂怎么办` | 整句自然语言 |
| 001 | `内存不够用了` | 歧义词跨 redis/java |
| 001 | `日志是怎么记录的` | 歧义词跨 mysql/kafka/redis |
| 001 | `为什么加了索引还是慢` | 跨文档：回表 / 索引失效 / EXPLAIN |
| 002 | `住宿费能报多少` | 另一个租户能正常检索 |
| 002 | `Redis 怎么配置淘汰策略` | **租户隔离**：不该看到 001 的技术文档 |
| 001 | `怎么申请年假` | **知识库外**：答案该是「没找到」 |

最后会校验所有召回结果的 `tenant_id`，串了租户直接 exit 1。

## 实测结果

```
租户隔离：✓ 9 条 query 全部只返回本租户数据
```

几个值得看的：

**向量检索生效** —— query「缓存里的数据同时失效导致数据库被打挂怎么办」
字面上和文档几乎不重叠，仍然把缓存雪崩、缓存击穿、缓存穿透三条都捞出来了：
```
#1 chunk-014 缓存穿透…    #2 chunk-016 缓存雪崩…    #3 chunk-015 缓存击穿…
答案：这是"缓存雪崩"问题…给缓存过期时间加上随机抖动，把失效时间打散。
      来源：redis-guide.pdf 第 53 页
```

**租户隔离生效** —— tenant-002 问 Redis，召回的全是 it/hr/finance，
而且 RRF 分只有 0.016 一档（远低于正常命中的 0.032），说明确实没东西可匹配。

**知识库外正确拒答** —— tenant-001 问年假，精排分全是 0，LLM 回了
「知识库中没有找到相关信息」。
