# 二、配置

```bash
# .env
LOG_LEVEL=INFO           # DEBUG 会额外打 Context 原文和完整 Prompt
LOG_FILE=logs/rag.log    # 留空则只输出到控制台
```

文件按大小滚动：单文件 10MB，保留 5 个历史文件。

# 三、日志格式

```
2026-09-04 00:30:28 INFO  [6bca573c] app.retriever   召回 10 条 | embed 18ms | es 32ms | …
└──────── 时间 ────────┘ └级别┘ └request_id┘ └─模块─┘ └──────── 内容 ────────┘
```

`request_id` 是这套东西的核心。一次问答会穿过 5 个模块，
没有它就分不清哪几行属于同一次请求 —— 尤其是并发的时候。

实现上用的是 `contextvars.ContextVar` 加一个 `logging.Filter`：

```
api.chat()  ──► new_request_id()  ──► 写进 ContextVar
                                            │
        各模块 logger.info(...)  ──► RequestIdFilter 自动读出来注入
```

好处是**不用把 request_id 一层层当参数传下去**，
retriever / reranker / llm 都不知道它的存在。

脚本里没有请求，显示为 `--------`。

# 四、追一次请求

响应里会带上 `request_id`：

```json
{ "answer": "…", "sources": [...], "request_id": "6bca573c" }
```

拿它去 grep：

```bash
grep 6bca573c logs/rag.log
```

```
INFO  [6bca573c] app.rag_service  RAG 开始 | tenant=tenant-001 top_k=3 debug=False | query='缓存雪崩怎么解决'
INFO  [6bca573c] app.retriever    召回 10 条 | embed 18ms | es 32ms | index=rag_app_chunks tenant=tenant-001 top_k=10
INFO  [6bca573c] app.reranker     精排 10 → 3 条 | 1ms | 最高分 0.571
INFO  [6bca573c] app.context      Context 拼装完成 | 3 个 Chunk | 261 字
INFO  [6bca573c] openai._base_client  Retrying request in 0.452704 seconds
INFO  [6bca573c] app.llm          LLM 生成完成 | model=qwen3.8-27b | 9302ms | token 输入 344 输出 114
INFO  [6bca573c] app.rag_service  RAG 完成 | 总计 9355ms = 召回 50 + 精排 1 + 生成 9303 | 引用 3 个 Chunk | 答案 73 字
```

> `request_id` 要在 `RAGResponse` 里声明才会出现在响应里。
> `response_model=RAGResponse` 会把模型没声明的字段过滤掉 ——
> 和之前 `debug` 字段踩的是同一个坑。

# 五、为什么重点记耗时

RAG 四个阶段的耗时差好几个数量级，出问题时第一件事就是看这一行：

```
总计 9355ms = 召回 50 + 精排 1 + 生成 9303
                                    └──► 99% 的时间在等 LLM
```

这个数字直接决定优化方向：

```
生成占大头   ──► 换小模型 / 开流式输出 / 砍 Context 长度
召回占大头   ──► 查 ES 慢查询 / 减 num_candidates / Embedding 换 GPU
精排占大头   ──► 说明用了 CrossEncoder，减候选数
```

召回那一步还拆成了两半，因为这两者的瓶颈完全不同：

```
embed 18ms   ← 本机 CPU 跑模型（首次调用会到 350ms，模型预热）
es    32ms   ← 网络 + ES 检索
```

# 六、主动告警的两处

不是所有异常都会抛出来，有些是"能跑但结果不对"：

```
召回为空          logger.warning  租户过滤后一条都没剩，多半是 tenant_id 传错
精排分全为 0      logger.warning  query 和候选文档一个 token 都没对上
```

实测「怎么申请年假」这条（tenant-001 没有 HR 文档）：

```
WARNING [6bcdacaf] app.reranker  精排分全为 0，候选与 query 无重叠：query='怎么申请年假'
```

LLM 那边则是三种情况分开记：

```
调用失败      logger.exception  带 traceback，然后原样 raise
返回空内容    logger.warning    附上 finish_reason，通常是被 max_tokens 截断
正常          logger.info       模型 / 耗时 / token 用量
```

token 用量记下来是为了**算钱**。生产环境按 request_id 聚合，
就能知道哪类问题最贵。

# 七、噪音压制

这几个库默认会把每次调用打成 INFO，全压到 WARNING：

```
elastic_transport.transport   每个 ES 请求的完整 URL
elasticsearch
httpx / httpcore
httpx2 / httpcore2            ← openai 3.x 用的是 vendored 的 httpx2，不是 httpx
sentence_transformers         启动时的模型加载信息
urllib3
```

`httpx2` 这个名字是实测发现的：只压 `httpx` 的话，
每次 LLM 调用还会多打一行完整的 API URL。

`openai._base_client` **故意没压** —— 它会打 `Retrying request`，
那是真正有用的信息（上面第四节的日志里就抓到一次重试）。

# 八、已知限制

```
多进程写同一个文件
    RotatingFileHandler 在多进程下滚动时可能互相覆盖。
    实测中就出现过：你的 uvicorn --reload 和我的测试服务
    同时写 logs/rag.log，日志里出现了两行"日志已初始化"。
    生产环境应改为每进程一个文件，或者交给 systemd/docker 收集 stdout。

没有采样
    每个请求都全量记录。QPS 高了以后 INFO 级别的量会很大，
    需要按比例采样或者把明细降到 DEBUG。

没有接入外部系统
    目前只有本地文件。真实项目通常输出 JSON 格式，
    由 Filebeat/Promtail 采集到 ELK 或 Loki。
```
