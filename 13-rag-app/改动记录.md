# 二、问题一：SimpleReranker 对中文完全失效

## 原来的写法

```python
query_words = set(query.lower().split())      # 按空格切
```

中文不用空格分词，于是：

```
"Redis maxmemory-policy 是什么"   （用户手动敲了空格）
  → {'redis', 'maxmemory-policy', '是什么'}    ← 还算能用

"Redis内存满了怎么淘汰"           （正常中文写法）
  → {'redis内存满了怎么淘汰'}                  ← 整句成了一个"词"
  → 所有文档得分都是 0
  → 排序等于没做，原样透传
```

这就是为什么跟 Redis 无关的 `java-gc.pdf` 也能留在 sources 里。

## 现在的写法

新增 `tokenize()`：英文按非字母数字切词，中文切**相邻两字**（bigram）。

```
"Redis内存满了怎么淘汰"
  → ['redis', '内存', '存满', '满了', '了怎', '怎么', '么淘', '淘汰']

chunk-002  命中 ['redis','内存','淘汰']  → 3/8 = 0.375
chunk-004  命中 ['内存']                → 1/8 = 0.125
```

**为什么用二元组不用单字**：单字太容易误命中 ——
「保**存**数据」里的「存」会让它和「内**存**」沾上关系。

**为什么分数改成覆盖率**（命中数 / query token 数）：
0~1 好读；长文档也不会因为词多而占便宜。

# 三、问题二：精排分根本没被写回去

```
SimpleReranker.rerank()   排完序，但没把分数写进 document
        ↓
ContextBuilder.build()    读的是 document["_score"]   ← ES 的 RRF 分
        ↓
响应里的 score = RRF 分，跟精排毫无关系
```

现在 `rerank()` 每条挂上 `_rerank_score`，`_score`（RRF 分）原样保留，
`ContextBuilder` 两个都取。于是能看出这是**两回事**：

```json
{
  "chunk_id": "chunk-002",
  "score": 0.032786883,     // ES 的 RRF 融合分
  "rerank_score": 0.375     // 精排分
}
```

# 四、debug 通道

## 为什么原来没有

两层原因：

```
① 四个模块都是静默执行，没有 logging/print
② 即使 rag_service 多返回了字段，也会被丢掉
   —— response_model=RAGResponse 只声明了 answer + sources，
      pydantic 序列化时把多余的 key 过滤掉了
```

所以加 debug **必须同时改 `models.py`**，光改 `rag_service.py` 没用。

## 怎么用

```bash
curl -X POST --noproxy '*' http://127.0.0.1:8000/api/rag/chat \
  -H 'Content-Type: application/json' \
  -d '{"query":"Redis内存满了怎么淘汰","tenant_id":"tenant-001",
       "top_k":3,"debug":true}'
```

默认 `debug=false` —— 它会把知识库原文和 Prompt 一起吐出来，生产环境别开。

## debug 里有什么

```
retrieval_size   Retriever 实际召回几条
retrieved        召回结果：rank + score + rerank_score(None)
reranked         精排结果：rank + score + rerank_score
context_chars    Context 字数
context          喂给 LLM 的 Context 原文
messages         实际发给 LLM 的 messages
```

**关键是对着看 retrieved 和 reranked 两份名次**，才知道精排改变了什么：

```
--- 召回（按 RRF 分）---            --- 精排后（按精排分）---
#1 chunk-002  score=0.032787        #1 chunk-002  rerank=0.375
#2 chunk-001  score=0.032258        #2 chunk-001  rerank=0.25
#3 chunk-004  score=0.031498        #3 chunk-004  rerank=0.125
#4 chunk-003  score=0.031498        （top_k=3 截掉）
```

只列 `chunk_id` 是不够的 —— 光看 id 换了顺序，看不出凭什么这么排。

# 五、顺带

- `rag_service.py` 里硬编码的 `top_k=10` 提成了常量 `CANDIDATE_SIZE`
- `models.py` 里 `debug` 用 `RAGDebug` 类型而不是 `dict[str, Any]`：
  前者能在 `/docs` 里显示结构，后者只显示成一团
- `main.py` 另有一处不相关的改动：自定义 `/docs` 注入字体 CSS
  （Swagger UI 的 CSS 要 Titillium Web / Open Sans，FastAPI 没引字体文件，
  浏览器回退到默认字体，有些机器上是手写体）

# 六、遗留

```
retrieval_size = 4     但 CANDIDATE_SIZE = 10
        │
        └──► 索引里总共只有 4 条数据，召回不满
                    │
                    └──► 4 条挑 3 条，精排能做的事很有限
                         等语料多起来（10 条挑 3 条）才看得出价值
```

其他没做的：

```
中文分词      ES 没装 IK 插件，BM25 侧中文被切成单字（见 12 课记录）
评估          没有 recall@k / nDCG，改了精排也不知道是不是真变好了
日志          仍然没有 logging，debug 只能靠请求参数拿
```
