# 一、顺序确认：先定类和 mapping，这时候还没有数据

**我的判断**：先定义 chunk 的类，和 ES 的 mapping，这个时候还没有写入数据。

**结论：成立。**

```
app/models.py        定义 DocumentChunk       chunk 长什么样
app/index_manager.py 定义 INDEX_NAME + mapping  ES 里字段是什么类型
app/init_index.py    调 create_index()         把空索引建出来
                              │
                              ↓
                    rag_chunks 索引存在，_count = 0
                              │
                              ↓
app/index_documents.py  ← 数据是这一步才进去的
```

## 但这一步没那么"无害"，两个反例

**① `dims: 512` 已经把 embedding 模型锁定了**

`index_manager.py:47` 写死了 `"dims": 512`，对应 `BAAI/bge-small-zh-v1.5` 的输出维度。
dims 在 ES 里**改不了**，换模型只能删索引重建。

所以"定 mapping"虽然没写数据，却是整条链路里**最难回退的一步**，不是准备工作。

**② `elasticsearch_client.py:19-21` 有模块级调试代码**

```python
# 调试代码
es = ElasticsearchClient()
print(es.ping())
```

任何 `import` 都会真的去连一次 ES 并打印。
所以严格说，"定义类"这一步已经在跟 ES 说话了。

# 二、空索引是不是就是 mapping？

**不完全等于，mapping 是空索引的一部分。**

```
空索引  =  mappings（字段定义，我写的）
        +  settings（分片副本等，ES 补的）
        +  aliases（别名，本课没用）
        +  底层空的倒排表 + 空的 HNSW 图
```

## 对应 MySQL 的类比

| ES 概念 | MySQL 类比 |
|---|---|
| 索引（index） | 表 |
| mapping | 表结构（`CREATE TABLE` 里的字段定义） |
| settings | 表的存储参数 |
| 文档（document） | 行 |

`init_index.py` 跑完 = `CREATE TABLE rag_chunks (...)` 执行完，表建好，0 行数据。

# 五、为什么写入需要 BAAI/bge-small-zh-v1.5，不能直接写？

**能直接写。但直接写就只有 BM25，没有向量检索了。**

mapping 里 7 个字段，**6 个是照抄，只有 1 个要算**：

```
chunk_id   → 照抄 documents.json          直接写 ✅
content    → 照抄                          直接写 ✅
source     → 照抄                          直接写 ✅
page       → 照抄                          直接写 ✅
category   → 照抄                          直接写 ✅
tenant_id  → 照抄                          直接写 ✅
embedding  → dense_vector(512)            ❌ 抄不出来
```

`documents.json` 里**没有 `embedding` 这个字段**。手上只有一句中文：

```
"Redis 的 maxmemory-policy 用于控制 Redis 内存达到 maxmemory 限制后如何淘汰数据。"
```

而 ES 要的是 512 个浮点数：

```
[0.0231, -0.0817, 0.0445, ..., 0.0192]
```

**从文字变成这 512 个数，就是模型干的活。ES 自己不会算。**
ES 只负责：存这 512 个数、给它建 HNSW 图、算两个向量之间的余弦距离。

## 如果不要模型会怎样

把 mapping 里的 `embedding` 字段删掉，`documents.json` 直接灌进去 —— 能跑，`keyword_search()` 也能搜。

代价：`vector_search()` 和 `hybrid_search()` 全废。
用户问"内存满了怎么淘汰"，文档里写的是"maxmemory-policy 淘汰数据"，字面不重合，BM25 搜不到。

**这正是第 12 课要解决的问题。**

## 一个致命前提：查询时必须用同一个模型

`api.py` 里 `embedding_service.embed(query)` 用的也是 `bge-small-zh-v1.5`。
写入用 A 模型、查询用 B 模型，向量不在同一个空间里，算出来的距离毫无意义。

# 六、dense_vector 是不是把 chunk 转成向量了？

**两处要纠正。**

## ① dense_vector 不做转换，它只是个"容器类型"

`dense_vector` 相当于告诉 ES：
"这个字段会收到一个 512 个浮点数的数组，你按向量的方式存，并给它建 HNSW 图。"

它**不会**把文字变成向量。转换发生在 Python 里，`embedding.py` 的 `self.model.encode(...)`。
ES 收到的时候，已经是算好的 512 个数了。

```
embedding.py（Python 进程）        Elasticsearch（:9200）
   文字 → 512 个数      ──发过去──→   存进 dense_vector 字段
   ★这里才是转换★                     ★这里只是存★
```

**一句话：模型负责算，`dense_vector` 负责装。**

## ② 转的不是整个 chunk，是 chunk 的 content 一个字段

`document_service.py:33`：

```python
texts = [document["content"] for document in documents]
```

只抽了 `content`。`source`（redis-guide.pdf）、`page`（15）、`category`、`tenant_id`
**没参与向量计算** —— 它们照原样存成 keyword / integer，用来 filter 和展示出处。

## 结果：同一段内容在一条文档里存了两份

```
content:   "Redis 的 maxmemory-policy 用于控制..."   ← 原文，给 BM25 查
embedding: [0.0231, -0.0817, ...]                    ← 同一段话的向量，给 kNN 查
```

一份给关键词搜，一份给语义搜 —— **这就是 hybrid search 两路并查的物质基础。**

## 补一个配套细节

`embedding.py` 里 `normalize_embeddings=True`，向量被归一化成单位长度。
这跟 mapping 里 `"similarity": "cosine"` 是配套的 —— 归一化之后余弦相似度等价于点积，ES 算距离更快。

# 七、两个脚本别混了

| 脚本 | 干什么 | 跑几次 |
|---|---|---|
| `init_index.py` | 建空索引（mapping） | 一次 |
| `index_documents.py` | 把 chunk + 向量写进去 | 每次数据变了就跑 |

**`init_index.py` 不写数据，只建骨架。写数据的是 `index_documents.py`。**

## index_documents.py 干的四件事

```python
es_client = ElasticsearchClient()                    # 1. 连 ES
embedding_service = EmbeddingService()               # 2. 加载模型
documents = document_service.load_documents("data/documents.json")   # 3. 读 4 个 chunk
document_service.index_documents(documents)          # 4. 算向量 + 写入
```

## 第 4 步展开（document_service.py）

```python
texts = [d["content"] for d in documents]            # 抽 content
embeddings = embedding_service.embed_batch(texts)    # 批量算向量

for document, embedding in zip(documents, embeddings):
    body = {
        "chunk_id":  document["id"],      # 注意：id → chunk_id 改了名
        "content":   document["content"],
        "source":    document["source"],
        "page":      document["page"],
        "category":  document["category"],
        "tenant_id": document["tenant_id"],
        "embedding": embedding,           # ★ 算出来的 512 维 ★
    }
    self.client.index(index=INDEX_NAME, id=document["id"], document=body)

self.client.indices.refresh(index=INDEX_NAME)        # 强制刷新，立刻可搜
```

## 最后那句 refresh() 值得留意

ES 默认每秒才刷新一次，写完立刻搜可能搜不到。
加了 `refresh()` 就是"写完马上能搜"，教学脚本里方便，
**生产环境批量灌数据时反而不该每次都调。**

# 八、一个索引能放多条记录吗？怎么放？

**能。`rag_chunks` 里现在就躺着 4 条，靠 `_id` 区分。**

## 实测数据

```bash
curl -s --noproxy '*' "http://127.0.0.1:9200/rag_chunks/_search?pretty&_source_excludes=embedding"
```

| `_id` | content | source | page | category |
|---|---|---|---|---|
| chunk-001 | Redis 是一个基于内存的… | redis-guide.pdf | 1 | redis |
| chunk-002 | Redis 的 maxmemory-policy… | redis-guide.pdf | 15 | redis |
| chunk-003 | Redis Cluster 通过多个节点… | redis-cluster.pdf | 8 | redis |
| chunk-004 | Java G1 垃圾收集器… | java-gc.pdf | 20 | java |

> `_source_excludes=embedding` 把 512 个数字藏掉了，不然屏幕会被刷满。

## 怎么放进去的：for 循环，一条一条 index()

```python
for document, embedding in zip(documents, embeddings):
    self.client.index(
        index=INDEX_NAME,        # 放进哪个索引 → rag_chunks
        id=document["id"],       # 这条记录的 _id → "chunk-001"
        document=body,           # 这条记录的内容
    )
```

跑 4 次 = 4 次 HTTP 请求，往同一个索引塞了 4 条。等价于 SQL：

```sql
INSERT INTO rag_chunks VALUES ('chunk-001', ...);
INSERT INTO rag_chunks VALUES ('chunk-002', ...);
INSERT INTO rag_chunks VALUES ('chunk-003', ...);
INSERT INTO rag_chunks VALUES ('chunk-004', ...);
```

## _id 的作用：主键 + 幂等

`id=document["id"]` 显式指定了 `_id`，带来一个好处：

**重复跑 `index_documents.py` 不会产生重复数据。**
同 `_id` 再写一次是覆盖，相当于 `INSERT ... ON DUPLICATE KEY UPDATE`。
`_count` 一直是 4 而不是 8、12，就是这个原因。

如果不传 `id`，ES 会随机生成（像 `x7Kp9ZQBa...`），那每跑一次就多 4 条重复数据。

## 生产环境的差别：Bulk API

一条一条 `index()` 是 4 次网络往返。真实项目里几万个 chunk 会用 Bulk：

```python
from elasticsearch.helpers import bulk
bulk(self.client, actions)   # 一次请求，几百条
```

本课只有 4 条，for 循环够了，但要知道这是**教学简化**。

# 十、查询时 embedding_service 干什么？

```python
results = search_service.hybrid_search(
    query=query,
    embedding_service=embedding_service,   # ← 这个
    tenant_id=tenant_id,
    top_k=top_k,
)
```

**它把 query 转成 512 维向量。** 但措辞要精确：

**这个向量不存进 `dense_vector`** —— 它是"尺子"，拿去跟索引里已存的 `dense_vector` 比距离，比完就丢。

`hybrid_search()` 第一行：

```python
query_vector = embedding_service.embed(query)     # ★ 用户的问题 → 512 维 ★
```

然后塞进 knn 那一路：

```python
"knn": {
    "field": "embedding",              # 跟索引里哪个字段比
    "query_vector": query_vector,      # ★ 用它去比 ★
    "k": 20,
    "num_candidates": 100,
    "filter": { "term": { "tenant_id": tenant_id } }
}
```

## 两边都要过模型，而且必须同一个

```
写入时（离线，跑一次）
  chunk 的 content ──bge-small-zh-v1.5──→ 512维 ──存入──→ embedding 字段

查询时（在线，每次请求）
  用户的 query     ──bge-small-zh-v1.5──→ 512维 ──比距离──→ 跟上面那些比
                     ↑ 同一个模型，同一个向量空间
```

## hybrid_search 里 query 被用了两次

```python
"match": { "content": query }        # ← 用原文，走 BM25
"query_vector": query_vector         # ← 用向量，走 kNN
```

同一个问题，一路查字面，一路查语义，最后 RRF 融合。
**所以 `embedding_service` 只服务于 kNN 那一路，BM25 那一路根本不需要它。**

# 十二、standard / knn / RRF 是不是都在 ES 服务端做的？

**是的，全都是。** 一次 HTTP 请求进去，融合好的 top_k 出来。

## 界线画在哪

```
Python 进程（你的代码）
  │
  │  ① embedding_service.embed(query)  ← 唯一在客户端做的计算
  │        "内存满了怎么淘汰" → 512 维
  │
  │  ② 拼一个 JSON（retriever / rrf / standard / knn 全是描述性的参数）
  │
  ├──── 一次 POST /rag_chunks/_search ────►
  │
  │                          ES 服务端（Java，:9200）
  │                            │
  │                            │  ③ filter tenant_id
  │                            │  ④ standard → Lucene BM25 打分
  │                            │  ⑤ knn      → 遍历 HNSW 图算余弦
  │                            │  ⑥ rrf      → 按排名融合两个列表
  │                            │  ⑦ size     → 截断 top_k
  │                            │
  ◄──── 返回 hits[] ───────────┘
  │
  │  ⑧ api.py 整理成 JSON 返回给用户（只是字段挑选，无计算）
```

**客户端只干一件计算：把 query 变成 512 维向量。剩下全是 ES 的。**

## 那一大坨嵌套字典是"指令"，不是"代码"

`hybrid_search()` 里的
`retriever` / `rrf` / `retrievers` / `standard` / `knn` / `rank_constant` / `rank_window_size`
—— **一个都不是 Python 在执行**。

它们全是描述性参数，原样序列化成 JSON 发过去，**由 ES 解析并执行**。

```python
response = self.client.search(
    index=INDEX_NAME,
    retriever={                      # ↓ 以下全部只是数据
        "rrf": {
            "retrievers": [
                {"standard": {"query": {"bool": {...}}}},   # 描述 BM25 那一路
                {"knn": {"field": "embedding", ...}}        # 描述 kNN 那一路
            ],
            "rank_constant": 60,
            "rank_window_size": 50,
        }
    },
    size=top_k,
)
```

对照第十一节的结论 —— `client.search()` 只是个 HTTP 客户端 —— 这两件事其实是同一件事：
**Python 端从头到尾没有检索逻辑，只有"把意图写成 JSON"。**

## 这就是第 11 课 → 第 12 课升级的实际含义

| | 第 11 课 hybrid-search | 第 12 课 elasticsearch-rag |
|---|---|---|
| BM25 | `keyword_search.py` 自己算 | ES 算 |
| 向量检索 | numpy 全量算余弦 | ES 的 HNSW |
| RRF 融合 | `fusion.py` 手写 | ES 的 `rrf` retriever |
| 截断 top_k | Python 切片 | ES 的 `size` |
| 多租户隔离 | 取回结果后 Python 过滤 | ES 的 `filter`（检索前就隔离） |

**第 11 课这些事全在 Python 里；第 12 课全搬到了 ES。**
这就是"从手写脚本升级成检索服务"的实际含义。

## 自己验证：完全不碰 Python，RRF 照样跑

```bash

  -H 'Content-Type: application/json' \
  -d '{"retriever":{"rrf":{"retrievers":[
        {"standard":{"query":{"match":{"content":"内存淘汰"}}}},
```

# 十三、rerank 也是 ES 做的吗？

**第 12 课根本没有 rerank。** 链路到 RRF 就结束了。

```bash
grep -rn -i "rerank" app/
# （无输出）
```

## 先把 RRF 和 Rerank 分开 —— 最容易混的地方

| | RRF（第 12 课有） | Rerank（第 12 课没有） |
|---|---|---|
| 干什么 | 把两个列表按**名次**合成一个 | 用模型对每条候选**重新打分** |
| 要不要模型 | 不要，纯算术 | 要，CrossEncoder |
| 看不看正文 | **不看**，只看 rank | **看**，query 和正文一起喂进模型 |
| 快慢 | 极快 | 慢，每条候选过一遍模型 |
| 在哪跑 | ES 服务端 | 模型在哪就在哪跑 |

RRF 的公式就一行：

```
score = Σ  1 / (rank_constant + rank)
```

`hybrid_search()` 里的 `"rank_constant": 60` 就是那个常数。

**RRF 压根不知道文档在讲什么**，它只知道"你在 BM25 里排第 3、在 kNN 里排第 7"。
所以 **RRF 是融合（fusion），不是精排（rerank）**。

## 第 11 课有 rerank，而且在 Python 里

`11-hybrid-search/app/reranker.py` 用 `BAAI/bge-reranker-base`（CrossEncoder），跑在 Python 进程里。

```
第 11 课：vector + keyword → fusion.py（RRF）→ reranker.py（CrossEncoder 精排）→ top_k
第 12 课：ES 里的 knn + BM25 → ES 的 rrf → top_k                    ← 到这就完了
```

**第 12 课把 RRF 搬进了 ES，但把 rerank 整个丢掉了。**
这是这一课的一个缺口，不是"搬到 ES 去做了"。

## Bi-Encoder vs CrossEncoder（为什么召回之后还要精排）

| | Bi-Encoder（`embedding.py` 用的） | CrossEncoder（`reranker.py` 用的） |
|---|---|---|
| 怎么算 | query 和 doc **各自**编码成向量，再算距离 | query 和 doc **拼成一个输入**喂给模型 |
| 交互 | 编码时两者没见过面，细粒度信息丢失 | 同一个注意力上下文里看完整文本 |
| 能否预计算 | 能，文档向量离线算好存 ES | 不能，每次都要现算 |
| 用在哪 | 召回（全库筛 Top-50~100） | 精排（候选里挑 Top-5~10） |

标准做法：**Bi-Encoder 先召回 Top-50~100，CrossEncoder 再精排取 Top-5~10 喂给 LLM。**

## ES 到底能不能做 rerank？

**能，但本机这套跑不了。** ES 8.x 有 `text_similarity_reranker` retriever：

```json
{
  "retriever": {
    "text_similarity_reranker": {
      "retriever": { "rrf": { "...": "..." } },
      "field": "content",
      "inference_id": "my-rerank-model",
      "inference_text": "内存满了怎么淘汰"
    }
  }
}
```

问题在 `inference_id` —— **ES 自己不跑 rerank 模型**。它要么调 Elastic 自家的 ELSER
（需要 ML 节点 + 白金授权），要么转发给外部服务（Cohere / HuggingFace 端点）。
本机这个单节点 ES 8.5 两个都没有。

## 结论：跟向量计算是同一个模式

```
算向量        → ES 不算，Python 算好发过去
算 rerank 分  → ES 也不算，要么外部服务，要么 Python 自己来
存 + filter + BM25 + kNN + RRF + 截断  → 这才是 ES 的活
```

**ES 是检索引擎，不是模型推理引擎。** 凡是"要过一遍神经网络"的事，默认都不在 ES 里。

## 想给第 12 课补上 rerank，最省事的做法

把第 11 课的 `Reranker` 搬过来，接在 `hybrid_search()` 后面：

```python
# search_service.py（示意，尚未实现）
hits = self.client.search(..., size=50)["hits"]["hits"]   # ES 先给 50 条候选
reranked = self.reranker.rerank(query, hits, top_k=5)      # Python 精排到 5 条
```

**两个必须注意的点：**

**① `size` 要从 5 放大到 50。** 精排的前提是**候选池够大**。
现在 `hybrid_search` 直接 `size=top_k`（5 条），没有留精排的空间 ——
5 条里精排 5 条，等于没排。

**② 输入结构要转换。** 第 11 课的 `rerank()` 吃的是
`{"document": Document, "score": float, "rank": int}`，
而 ES 返回的是 `{"_source": {...}, "_score": float}`。
直接传会在 `result["document"].content` 上报 KeyError，中间要加一层适配。

## 完整链路应该长什么样

```
用户 query
   │
   ├─► Bi-Encoder（bge-small-zh-v1.5）→ 512 维
   │
   ↓  一次请求进 ES
┌──────────────────────────────────┐
│ ① filter tenant_id               │
│ ② BM25   ③ kNN     两路并行       │
│ ④ RRF 融合                        │
│ ⑤ size = 50        ← 放大候选池    │
└──────────────┬───────────────────┘
               ↓  50 条候选回到 Python
   CrossEncoder（bge-reranker-base）逐条打分   ← ⚠️ 本课缺这一步
               ↓
            top_k = 5
               ↓
      拼 prompt → LLM → 回答            ← ⚠️ 本课也没有
```

## 1. DocumentChunk 是死代码

```bash
grep -rn "DocumentChunk" app/
# app/models.py:5:class DocumentChunk:      ← 只有定义，零引用
```

`load_documents()` 返回 `list[dict]`，`index_documents()` 也吃 `dict`，
`document_service.py:56` 手写 `"chunk_id": document["id"]` 做映射。

而且字段名不一致：dataclass 叫 `id`，mapping 叫 `chunk_id`，`api.py:38` 又读 `_source["chunk_id"]`。

**"chunk 的形状"同时被记在四个地方**（dataclass、mapping、写入体、api 返回），靠人肉对齐。

**建议**：保留它当"契约文档"，但在文件里注明"本类不参与运行，仅作契约说明"，
否则下一个读代码的人会以为它在链路里，去改它然后发现毫无效果。

## 2. content 字段没有中文分词器

mapping 里是 `"content": {"type": "text"}`，没给 `analyzer`。
ES 默认用 `standard` analyzer，**对中文是按单字切的**。

`chunk-002` 在倒排表里存的是：

```
redis / 的 / maxmemory / policy / 用 / 于 / 控 / 制 / 内 / 存 / ...
```

后果：用户问"内存满了怎么淘汰"，BM25 是拿"内""存""满""了""怎""么""淘""汰"
这些单字去撞的，精度很差。

**注意这个因果关系**：`简易流程图.md` 里写的"BM25 擅长专有名词，kNN 擅长换句话说"，
在当前 mapping 下**恰好是对的** —— 但它成立的原因不是 BM25 的天性，
而是**没装中文分词器**。

装 `ik_max_word` / `smartcn` 能改善，代价是引入插件依赖。教学项目里认下来即可，但要知道原因。

## 3. create_index() 幂等但不可演进

```python
if self.client.indices.exists(index=INDEX_NAME):
    return
```

重复跑安全，但**索引一旦建出来，mapping 就永远冻在第一次的样子**。

现在没有任何一步负责处理"索引已存在但 schema 旧了"。
