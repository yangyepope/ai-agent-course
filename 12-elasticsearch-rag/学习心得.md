11 个 py 文件，按"会不会主动干活"分成 3 类：

```
                    ┌──► 能力层（只定义 class，被别人调用）
                    │      elasticsearch_client / index_manager
                    │      embedding / document_service
                    │      search_service / models
                    │
11 个 py 文件 ──────┼──► 一次性脚本（有 main()，跑完就退）
                    │      test / init_index / index_documents

```
建索引 + 灌数据  ──► 离线 ──► 跑一次就行  ──► 将来是定时任务/MQ 消费者
搜索             ──► 在线 ──► 一直响应请求 ──► 将来是常驻 API 服务
```

## 2.3 为什么顺序不能错

```
test.py         ──► 得到 dims = 512
   │
   │ 【不知道 512，mapping 写不出来】
   ↓
init_index.py   ──► 建索引，声明 dense_vector(512)
   │
   │ 【不建索引直接写，ES 的 dynamic mapping 会把 embedding 猜成 float 数组
   │   → 写入阶段静默成功，等到查询才报
   │     "[knn] queries are only supported on [dense_vector] fields"
   │   → 坑在「发现得晚」，不在「查不出原因」】
   ↓
index_documents ──► 写数据
   │
   │ 【没数据，搜出来是空数组】
   ↓
uvicorn         ──► 开始搜
```

改 mapping 的流程（ES 的 mapping **不可原地修改**）：

```
想改 dims / 字段类型
        │
        ↓
DELETE /rag_chunks      ← 必须先删！create_index() 里有 if exists: return
        │
        ↓
改 index_manager.py（dims）+ embedding.py（model_name）
        │
        ↓
python -m app.init_index
        │
        ↓
python -m app.index_documents   ← 数据也得重灌
```

# 三、每个模块具体做什么

## 3.1 `app/test.py` —— 冒烟测试

```
SentenceTransformer("BAAI/bge-small-zh-v1.5")
        │
        ├──► 能加载吗？（首次自动从 HuggingFace 下载 ~100MB）
        │
        └──► get_embedding_dimension() ──► 512
```

**唯一目的**：拿到 512 这个数字。

```
bge-small-zh-v1.5  ──► 512 维
bge-base-zh        ──► 768 维
bge-large-zh       ──► 1024 维
        │
        └──► 换模型 ──► dims 变 ──► 必须重建索引
```

> API 更名：`get_sentence_embedding_dimension()`（旧）→ `get_embedding_dimension()`（5.x 起）

## 3.2 `app/models.py` —— 数据结构

```
@dataclass DocumentChunk
        │
        └──► id / content / source / page / category / tenant_id
```

现在**没被任何代码 import**，是一个"字段清单备忘录"。
但文件末尾那段注释才是重点:

```
现在：       tenant_id
                │
后续可能：      ├──► department_id
                ├──► user_id
                ├──► permission
                ├──► document_id
                └──► knowledge_base_id
                        │
                        └──► 每加一个 ──► 多一个 ES filter 条件
```

它在提前告诉你：真实 RAG 不是"搜得准就行"，而是
**"在这个人能看到的范围内，搜得准"**。

## 3.3 `app/elasticsearch_client.py` —— 连接层

```
ElasticsearchClient(url="http://127.0.0.1:9200")
        │
        ├──► get_client() ──► 原生 Elasticsearch 对象（交给别人用）
        │
        └──► ping()       ──► bool（探活）
```

职责单纯到只有一件事：

```
全项目 ──► 只有这一个文件知道 ES 地址
                │
                └──► 以后要：加账号密码 / 加 TLS / 换集群多节点 / 调连接池
                            │
                            └──► 只改这 1 个文件，其他 10 个文件一行不动
```

> ⚠️ **现存问题（只记录，不改）**：文件末尾有模块级调试代码
> ```
> es = ElasticsearchClient()
> print(es.ping())
>         │
>         └──► 任何文件 import 它 ──► 都会建一次连接 + 打印一行 True/False
>                     │
>                     └──► api.py / init_index.py / index_documents.py 全受影响
> ```
> 正确做法：像 `search_service.py` 那样包进 `if __name__ == "__main__":`。

## 3.4 `app/index_manager.py` —— 索引层（最该理解的文件）

```
INDEX_NAME = "rag_chunks"
        │
        ├──► document_service.py import 它 ──► 往这里写
        └──► search_service.py   import 它 ──► 从这里读
                    │
                    └──► 写入和读取指向同一索引，靠常量而不是复制字符串
```

**同一份文档 → 两个字段 → 两条检索路径**（整课骨架）：

```
                 一个 ES Document
                        │
           ┌────────────┴────────────┐
           ↓                         ↓
        content                  embedding
      type: text            type: dense_vector
           │                    dims: 512
           ↓                    similarity: cosine
      分词 + 倒排索引                  │
           │                         ↓
           ↓                     HNSW 图
         BM25                       kNN
           │                         │
           ↓                         ↓
       字面命中                   语义相近
   "maxmemory-policy"        "内存满了怎么办"
```

mapping 里每个类型的选择理由：

```
用来「搜」的 ──► text     ──► content
                              │
                              └──► 会分词 ──► BM25 能用

用来「筛」的 ──► keyword  ──► chunk_id / source / category / tenant_id
                              │
                              └──► 不分词、精确匹配 ──► filter/聚合能用

用来「算」的 ──► integer  ──► page ──► 可范围查询

用来「量距离」的 ──► dense_vector ──► embedding ──► kNN
```

**text vs keyword 是 ES 基本功**：

```
source = "redis-guide.pdf"
        │
        ├──► 若定为 text    ──► 切成 redis / guide / pdf
        │                          └──► ✗ 没法精确过滤"只要这个文件"
        │
        └──► 定为 keyword   ──► 整串当一个词
                                   └──► ✓ term filter 精确命中
```

**配套关系**（这两个必须一起看）：

```
embedding.py: normalize_embeddings=True   （向量归一化）
                        ↕  配套
index_manager: similarity="cosine"
                        │
                        └──► 归一化后余弦 ≡ 点积 ──► 更快更稳
```

## 3.5 `app/embedding.py` —— 向量层

```
embed(text)          ──► list[float]        ──► 单条，给 query 用
embed_batch(texts)   ──► list[list[float]]  ──► 批量，给灌数据用
```

为什么分两个方法：

```
灌数据（几百上千条） ──► embed_batch ──► 矩阵一次算完 ──► 快得多
查询（永远只 1 条）  ──► embed       ──► 没必要包一层 list
```

`.tolist()` 是必须的：

```
model.encode() ──► numpy array
                        │
                        │ 【numpy 类型不能 JSON 序列化】
                        ↓
                   .tolist() ──► Python list ──► 才能发给 ES
```

**铁律**：

```
写入用模型 A ──► 向量落在空间 A
查询用模型 B ──► 向量落在空间 B
                    │
                    └──► 空间不同 ──► 检索结果 = 纯噪声
                            │
                            └──► 写入和查询必须同一个模型！
```

## 3.6 `app/document_service.py` —— 写入层

```
load_documents(path)
        │
        └──► json.load ──► list[dict]
                                │
                                ↓
index_documents(documents)
        │
        ① 抽 content    ──► texts
        │
        ② embed_batch   ──► embeddings
        │
        ③ zip 配对      ──► 拼 body ──► client.index() 逐条写
        │
        ④ refresh()     ──► 立刻可搜
```

三个细节：

```
① id=document["id"]
        │
        └──► chunk 的 id 当成 ES 的 _id
                    │
                    └──► 重复灌数据 = 覆盖（不是产生重复文档）
                                │
                                └──► 脚本可放心重跑（幂等）

② chunk_id 字段又存了一遍 id
        │
        └──► 因为 ES 的 _id 是元数据，_source 里默认不含它
                    │
                    └──► 存一份进 _source ──► api.py 才能 hit["_source"]["chunk_id"]

③ indices.refresh()
        │
        └──► ES 默认 1 秒刷一次
                    │
                    ├──► 不刷 ──► 灌完立刻搜 ──► 搜不到（学习时以为代码错了）
                    └──► 生产大批量导入 ──► 反而要关掉 refresh 提速
```

> 可优化点：`for` 循环逐条 `client.index()`
> ```
> 4 条    ──► 没问题
> 上万条  ──► 应换 helpers.bulk（一次请求发一批）──► 快几十倍
> ```

## 3.7 `app/search_service.py` —— 检索层（三种检索的演进史）

这个文件按"演进顺序"保留了三个方法:

```
第一层 keyword_search  ──► BM25              ──► 字面准，换说法就废
            │
            ↓ 补短板
第二层 vector_search   ──► kNN               ──► 语义准，专有名词就废
            │
            ↓ 两个一起上
第三层 hybrid_search   ──► BM25 + kNN + RRF  ──► ✓ API 用的就是这个
```

### 第一层：`keyword_search` —— BM25

```
query={"bool": {
    "must":   [ match content ]  ──► 参与打分，影响排序
    "filter": [ term tenant_id ] ──► 不打分，只判断要不要，结果可缓存 → 更快
}}
```

**must vs filter 的判断标准**：

```
这个条件影响「排多前」吗？
        │
        ├──► 是 ──► must    ──► 内容相关性（match content）
        │
        └──► 否 ──► filter  ──► 硬性范围（tenant_id / category / 时间）
                        │
                        └──► 租户隔离属于「要不要」 ──► 必须放 filter
```

文件里注释掉的第一版**没有 filter**:

```
第一版 keyword_search（已注释）
        │
        └──► 只有 match content，没有 tenant_id
                    │
                    └──► ✗ 跨租户泄漏数据 ──► RAG 上生产最容易犯的安全事故
```

```
优点 ──► 精确词 / 专有名词 / 型号 / 错误码 命中率极高（"maxmemory-policy"）
缺点 ──► 换个说法就搜不到（问"内存满了怎么办" ✗ 搜不到 "maxmemory-policy"）
```

### 第二层：`vector_search` —— kNN

```
knn={
  field: "embedding"
  query_vector: [512 维]
  k: top_k
  num_candidates: 50
  filter: term tenant_id
}
```

**`k` 和 `num_candidates` 的区别（高频面试题）**：

```
      整个索引的向量
            │
            ↓  HNSW 图粗捞
      num_candidates = 50
       （Candidate Pool）
            │
            ↓  精算排序
          k = 5
       （最终返回）
```

```
num_candidates 越大 ──► 召回越准，但越慢
num_candidates 越小 ──► 越快，但可能漏掉真正的最近邻
            │
            └──► 铁律：num_candidates > k，一般 5~10 倍
                        │
                        └──► kNN 是「近似」搜索（ANN），不是精确的
```

**kNN 的 filter 是 pre-filter（先过滤再搜）**：

```
先 filter tenant_id ──► 缩小候选集 ──► 再在里面找最近邻   ✓ ES 的做法
                              vs
先找 top 50 ──► 再筛 tenant_id ──► 可能一条不剩          ✗ 灾难
```

```
优点 ──► 语义相近就能召回，同义词、换句话说都行
缺点 ──► 专有名词/缩写/编号反而不准（向量里 chunk-001 和 chunk-002 几乎一样）
```

### 第三层：`hybrid_search` —— RRF 融合

BM25 和 kNN 的短板**正好互补**:

```
                    query
                      │
           ┌──────────┴──────────┐
           ↓                     ↓
   standard retriever      knn retriever
   （BM25 + filter）       （向量 + filter）
           │                     │
           ↓                     ↓
        榜单 A                 榜单 B
      ①chunk-002            ①chunk-002
      ②chunk-001            ②chunk-003
      ③chunk-003            ③chunk-004
           │                     │
           └──────────┬──────────┘
                      ↓
                  RRF 融合
           rank_constant   = 60
           rank_window_size = 50
                      │
                      ↓
         score = Σ 1/(60 + rank)
                      │
                      ↓
                  最终 top_k
```

**RRF（Reciprocal Rank Fusion）为什么好用**：

```
BM25 分数 = 12.7  ──┐
                    ├──► 量纲完全不同 ──► 直接加权求和 ──► 要调参 + 易被异常值带偏
kNN  分数 = 0.89  ──┘

RRF 只看「排名」不看「分数」
        │
        ├──► 两个榜单都靠前 ──► 得分最高（两边都认可）
        ├──► 只在一个榜单靠前 ──► 也能进来（不会被另一路淹没）
        ├──► rank_constant=60   ──► 论文经验值，越大越"温和"（拉平榜单差距）
        └──► rank_window_size=50 ──► 每个 retriever 各取前 50 名参与融合
```

**对比第 11 课**：

```
第 11 课 ──► ES 查两次 ──► 结果拉回 Python ──► 自己写 RRF 算
                                │
                                └──► 2 次网络往返 + 自己维护的代码

第 12 课 ──► 一次 ES 请求 ──► ES 内部 RRF ──► 直接返回融合结果
                                │
                                └──► 1 次往返 + 0 行融合代码   ← 用生产级组件的价值
```

## 3.10 `app/api.py` —— HTTP 层

**为什么三个对象在函数外面（模块级）**：

```
写在模块级（现在这样）
        │
        └──► 服务启动时 ──► 加载模型 1 次 + 建连接 1 次
                    │
                    └──► 每个请求复用 ──► 响应几十毫秒   ✓

写进 search() 函数里
        │
        └──► 每个请求 ──► 重新加载 100MB 模型 + 重建连接
                    │
                    └──► 一次请求好几秒                  ✗
```

`search()` 只做两件事：

```
search(query, tenant_id, top_k)
        │
        ├──► ① 调 search_service.hybrid_search(...)
        │
        └──► ② 把 ES 原始返回「翻译」成对外契约
                    │
                    ├──► hit["_score"]                ──► score   ⚠️ 在 _source 外面
                    ├──► hit["_source"]["chunk_id"]   ──► id
                    ├──► hit["_source"]["content"]    ──► content
                    ├──► hit["_source"]["source"]     ──► source
                    ├──► hit["_source"]["page"]       ──► page
                    │
                    └──► 丢掉 _index / _shard / took / max_score 等内部字段
                                │
                                └──► API 层的职责 = 内部结构 → 对外契约
```

# 四、这一课真正学到的东西

## 4.1 分层：每个文件只有一个理由会被修改

```
换 ES 地址 / 加认证 / 换集群  ──► 只改 elasticsearch_client.py
换 Embedding 模型            ──► 只改 embedding.py（+ 重建索引改 dims）
加字段 / 改字段类型           ──► 只改 index_manager.py
换写入方式（改用 bulk）       ──► 只改 document_service.py
调检索策略（加 rerank 等）    ──► 只改 search_service.py
改接口出参格式               ──► 只改 api.py
加新接口                     ──► 加 router，main.py 不动
```

不是"为了好看而分层"，而是**改动不会扩散**。

## 4.2 依赖注入：谁创建，谁传入

```
错误做法：
  SearchService.__init__ 里 self.client = Elasticsearch("http://...")
        │
        └──► 每个 service 各建一个连接 + 地址散落各处 + 无法测试

现在的做法：
  ElasticsearchClient() ──► get_client() ──┬──► SearchService(client)
                                           └──► DocumentService(client, embedding)
        │
        ├──► 一个连接被多个 service 共享
        └──► 测试时能塞一个假 client 进去
```

## 4.3 多租户 filter 是安全底线

```
keyword_search ──► filter tenant_id  ✓
vector_search  ──► filter tenant_id  ✓
hybrid_search  ──► 两个 retriever 各自 filter tenant_id  ✓
        │
        └──► 一个都没漏（被注释的第一版是反面教材）

顺序铁律：先隔离 ──► 再检索 ──► 再排序
                │
                └──► 隔离没做好，检索做得再准都是灾难
```

## 4.4 mapping 是不可变的契约

```
dims 写死 512      ──► 换模型 ──► 必须重建索引
类型定为 keyword    ──► 想改 text ──► 必须重建索引
        │
        └──► ES 的 mapping 不能原地改
                    │
                    ├──► 所以上线前必须把字段和维度想清楚
                    ├──► 或者用 alias + 双写做索引滚动升级
                    └──► 这也解释了为什么 test.py 这个小脚本要排第一步
```

# 六、离生产还差什么

| 缺什么 | 现在 | 生产要做的 |
|---|---|---|
| 配置管理 | ES 地址、模型名硬编码 | 环境变量 / pydantic-settings |
| 批量写入 | `for` + `client.index()` | `helpers.bulk` |
| 中文分词 | ES 默认分词器（单字切分） | IK 分词器，BM25 才准 |
| 权限 | 只有 tenant_id | + department / user / permission |
| Rerank | RRF 后直接返回 | 接 CrossEncoder 精排（第 11 课学过） |
| 生成 | 只有检索，没有 LLM | top_k → prompt → LLM |
| 可观测 | 无 | 日志、检索耗时、召回率评估 |
| 调试代码 | `elasticsearch_client.py` 模块级 print | 挪进 `__main__` |

**最后一点最重要**：

```
        R E T R I E V A L   A U G M E N T E D   G E N E R A T I O N
                 │                    │                  │
                 ↓                    ↓                  ↓
        ✓ 这一课做完了            ✗ 还没做           ✗ 还没做
        （BM25+kNN+RRF+租户）   （拼 prompt）      （调 LLM）
                 │
                 └──► 这一课叫 elasticsearch-rag，其实只做完了 R
                            │
                            └──► 但价值就在这：R 这一层，现在是能上生产的了
```

下一步闭环:

```
/api/retrieval/search ──► top_k chunks ──► 拼进 prompt ──► LLM ──► 带出处的回答
```
