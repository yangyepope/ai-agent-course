```

            ↓

            ↓

            ↓

   改 chunk_size 512 → 256
            ↓
   跑 evaluate.py（10 个 case，7 个指标）
            ↓
   Recall 0.50 → 0.70，Precision 0.12 → 0.11
            ↓
   召回变好、精度略降 → 可接受，上线
```

# 二、这一课最重要的一个设计修正

## 2.1 错误做法：Evaluation 自己重新实现一遍 RAG

很多人写评估脚本会这样：

```
evaluate.py
   │
   ├── 自己 load embedding 模型
   ├── 自己连 ES
   ├── 自己写检索逻辑
   └── 自己拼 prompt
```

问题在于：**你评的不是线上那个 RAG，是评估脚本里的另一个 RAG。**

```
线上 RAG：  Query → Embedding → ES → Rerank → Top5
评估脚本：  Query → Embedding → ES → ✗忘了 Rerank → Top5
                                     │
                                     └──► 评出来的分数跟线上没关系
```

## 2.2 正确做法：RAG 暴露接口，Evaluation 只负责调用

```
class RAGService:

    def retrieve(self, query, top_k) -> list[dict]:   ← 评估的入口
        Query → Embedding → Vector Search → Rerank → Top K

    def answer(self, query, top_k) -> dict:            ← 评估的入口
        retrieve() → Context → Prompt → LLM → Answer
```

```
RAGEvaluator
     ↓  调用（不重新实现）
RAGService.retrieve() / answer()
     ↓
Retrieved Documents / Answer
     ↓
计算指标
```

**一句话记：Evaluation 是"外部观察者"，不是"平行实现"。**
线上改了 Rerank，评估分数自动跟着变 —— 这才叫评估。

# 三、七个指标，分别回答什么问题

```
                    evaluation_dataset.json
                              │
                              ▼
                        RAGEvaluator
                              │
                              ▼
                    RAGService.retrieve()
                              │
                    Retrieved Documents
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
      Retrieval Metrics              Context Construction
      （不用 LLM，纯计算）                     │
              │                               ▼
   ┌──────┬───┴───┬──────┐                   LLM
   ▼      ▼       ▼      ▼                    │
Recall Precision MRR   NDCG                   ▼
                                            Answer
                                              │
                                              ▼
                                          LLM Judge
                                （没标准答案可比，只能让模型判）
                                              │
                              ┌───────────────┼───────────────┐
                              ▼               ▼               ▼
                          Relevance     Faithfulness    Correctness
```

## 3.1 检索段：四个指标是四个不同的问题

| 指标 | 回答的问题 | 只看 | 变差说明 |
|---|---|---|---|
| **Recall@K** | 该找的，找到了几个？ | 收了多少 | 召回漏了，考虑加大 K / 换 Embedding |
| **Precision@K** | 找回来的，有几个是对的？ | 收了多少 | 噪音太多，Context 会被垃圾撑满 |
| **MRR** | 第一个正确答案排第几？ | 排得多前 | 对的在第 5 位，LLM 可能看不到 |
| **NDCG@K** | 整体排序合不合理？ | 排得多前 | Rerank 没起作用 |

**Recall / Precision 是"收了多少"，MRR / NDCG 是"排得多前"** —— 这是两类完全不同的能力。

一个具体例子（本课 q002）：

```
relevant：  redis-002
retrieved： redis-001  redis-002  redis-003  redis-004  redis-005
                          ↑
                       排第 2

Recall@5    = 1/1  = 1.00   ← 满分！该找的都找到了
Precision@5 = 1/5  = 0.20   ← 4 个是噪音
MRR         = 1/2  = 0.50   ← 但它排第 2，不是第 1
NDCG@5      =        0.63   ← 排序不理想
```

**Recall 满分不代表检索好。** 这就是为什么要四个指标一起看。

## 3.2 MRR 为什么"只认第一个"

```
relevant：  C、D
retrieved： A  B  C  D
                  ↑  ↑
                  │  └── D 也召回了，Recall 记它一功
                  └───── C 是第一个正确答案

RR = 1/3
```

D 排在 C 后面，对"LLM 能不能看到正确答案"毫无额外贡献 —— MRR 认为它不算数。

## 3.3 生成段：为什么必须用 LLM 当裁判

```
Ground Truth： "可以通过 maxmemory 参数设置 Redis 的最大内存限制。"
Answer：       "Redis 用 maxmemory 这个配置项来限制内存上限。"
                    ↓
            字符串比对：完全不一样，0 分
            语义比对：  说的是同一件事，1 分
```

没法用 `==` 判，也没法用正则判，**只能让模型判**。

| 指标 | 拿什么比 | 抓什么问题 |
|---|---|---|
| **Answer Relevance** | Answer ↔ Question | 答非所问 |
| **Faithfulness** | Answer ↔ **Context** | **幻觉**（编了 Context 里没有的话） |
| **Correctness** | Answer ↔ Ground Truth | 事实错了 |

**Faithfulness 是三个里最值钱的**，因为它是唯一能自动抓幻觉的指标：

```
Faithfulness 低 + Correctness 高   →  蒙对了，但没依据（下次就蒙不对）
Faithfulness 高 + Correctness 低   →  忠实于 Context，但 Context 本身检索错了
                                       └──► 问题在检索段，不在生成段
Faithfulness 低 + Correctness 低   →  在编
```

注意 Faithfulness 比的是 **Context**，不是 Ground Truth —— 所以 `evaluate_generation()`
里拼 context 时，必须和喂给 LLM 的完全一致，否则这个指标就没意义了。

## 4.1 定位：MockRetriever 的中文分词 bug

`mock_retriever.py` 的打分逻辑：

```python
for word in query.split():     # ← 问题在这
    if word in content:
        score += 1
```

`split()` 按空格切词。**中文不用空格分词**，于是：

```
"Redis 如何设置密码？".split()
        ↓
["redis", "如何设置密码？"]
        ↓
"redis"        → 11 个 chunk 全都包含   → 人人都得 1 分
"如何设置密码？" → 没有任何 chunk 整段包含 → 人人都得 0 分
        ↓
11 个文档全部 score = 1
        ↓
sort 是稳定排序，分数相同保持原顺序
        ↓
永远返回 documents[:5] = redis-001 ~ 005
```

而 q004 / q005 之所以正常，纯粹是因为问题里有 **英文缩写**：

```
"Redis 的 RDB 是什么？".split() = ["redis", "的", "rdb", "是什么？"]
                                              ↑
                                        这个 token 有区分度

redis-005（讲 RDB）  score = 3  ← 真的排到了第 1
其他                  score = 1~2
```

**结论：这个检索器实际上只是个"文档里有没有 redis 这个词"的匹配器。**
`Recall@5 = 0.50` 这个数字里，有 3 分是靠 relevant chunk 恰好排在前 5 位蒙到的。

## 4.2 这件事本身就是这一课的答案

```
如果没有 Evaluation：

   跑几个 demo，q001 q004 q005 都答对了
            ↓
   "检索效果不错嘛"
            ↓
   上线，中文问题全军覆没

有了 Evaluation：

   Recall 0.50 / MRR 0.38 / NDCG 0.42
            ↓
   打开 details，发现 8 题结果完全相同
            ↓
   5 分钟定位到 split() 不支持中文
```

**指标不是用来打分的，是用来定位问题的。**
所以 `evaluation_result.json` 一定要存每题明细 —— 汇总数字只告诉你"有病"，明细才告诉你"病在哪"。

# 五、写代码时踩的四个坑

## 5.1 NDCG 的 ideal 算错，会让"漏召回"拿到虚高分

`ndcg_at_k()` 内部是把传进来的列表排序当作 ideal。
如果只把**召回到的**文档翻译成分数，没召回的那些就不在列表里，ideal 被算小了：

```
relevant：   A、B
retrieved@5：X  A  X  X  X

天真做法： [0, 1, 0, 0, 0]
          ideal 排序 = [1, 0, 0, 0, 0]        ← ideal 只认了 1 个相关文档
          NDCG = 0.63 / 1.00 = 0.63           ← 虚高！B 根本没召回却没被罚

正确做法： [0, 1, 0, 0, 0, 1]                  ← 把漏掉的 B 补在 k 位之后
                          ↑ 第 6 位，不影响 actual DCG（只算前 5）
          ideal 排序 = [1, 1, 0, 0, 0, 0]     ← ideal 认了 2 个
          NDCG = 0.63 / 1.63 = 0.39           ← 这才是真实水平
```

这就是 `build_relevance_scores()` 存在的理由：补 0 补到 k 位（保证前 k 位是真实检索结果），
再把漏召回的相关文档追加在后面（只抬 ideal，不动 actual）。

## 5.2 LLM Judge 的输出不能直接 json.loads

模型爱干这三件事：

````
```json                          ← 加 Markdown 围栏
{"faithfulness": 0.8}
```

好的，我的评价如下：            ← 前后加解释文字
{"faithfulness": 0.8}

我拒绝回答                       ← 干脆不给 JSON
````

`json.loads()` 直接抛异常，**一个 case 崩掉整轮评估就死了** —— 前面 9 题白跑。
所以 `judge.py` 做了三级兜底：

```
去 Markdown 围栏
     ↓ 失败
正则抠出第一个 {...}
     ↓ 失败
返回全 0 分，把原始输出塞进 reason
     ↓
整轮评估继续跑完，事后看 reason 排查
```

## 5.3 temperature 必须是 0

```
temperature = 0.7  →  同样的代码跑两遍，分数不一样
                       ↓
                  你改了 chunk_size，分数从 0.72 变成 0.68
                       ↓
                  是改坏了？还是模型今天心情不好？——— 无法判断
```

**Evaluation 的第一要求是可复现。** 生成答案和当裁判，两处都要 `temperature=0`。

## 5.4 同一个模型既当选手又当裁判

`scripts/evaluate.py` 现在是同一个 `llm` 实例传给 `RAGService` 和 `LLMJudge`：

```
llm = create_llm()

rag_service = create_rag_service(llm)        ← 它写答案
judge       = LLMJudge(llm=llm)              ← 它给自己的答案打分
```

**模型会倾向于给自己的输出打高分。** 本课为了简单先这么写，
真实项目里 Judge 应该换一个更强的、不同的模型。

# 七、这一课真正学到的东西

## 7.1 评估集是资产，不是测试代码

```
app/*.py                  →  代码，随时可以重写
evaluation_dataset.json   →  资产，是人一条条标出来的
```

10 条太少了（本课够用），真实项目至少 100~300 条，而且要覆盖：

```
简单事实题     "Redis 如何设置密码"        ← 检索得到就该答对
多跳题         "淘汰策略有哪些，分别啥区别"  ← 要召回多个 chunk
拒答题         "Redis 的作者是谁"          ← 知识库里没有，应该说不知道
              └──► 这类题最重要，专门抓幻觉
```

## 7.2 先有指标，再谈优化

```
Recall 低   →  召回没找到  →  换 Embedding / 加大 K / 改 chunk 策略
Recall 高
但 MRR 低   →  找到了没排前 →  加 Rerank
Precision 低 →  噪音多      →  减小 K / 加过滤
Faithfulness 低 →  在编     →  改 Prompt（强调只能依据 Context）
Correctness 低
但 Faith 高  →  忠实但答错  →  问题在检索段，不在生成段
```

**每一个指标都对应一个明确的下一步动作。** 这才是指标的价值。

## 7.3 分层让评估变得可测

```
metrics.py   纯函数   →  单元测试 0.02 秒跑完，改一行立刻验证
judge.py     依赖 LLM →  用 StubLLM 就能测解析逻辑，不用真调模型
evaluator.py 只调度   →  没有业务逻辑，出错必然在上面两层
```

`test_judge.py` 用 `StubLLM` 测了四种 LLM 输出格式 —— **测容错逻辑，不需要真 LLM。**

# 八、离生产还差什么

| 缺什么 | 现在 | 生产要做的 |
|---|---|---|
| 检索器 | MockRetriever（中文都切不了词） | 接 13 课的 ES + 向量检索 |
| 评估集规模 | 10 条 | 100~300 条，含拒答题 |
| 标注 | 手写 relevant_chunks | 半自动：LLM 生成 + 人工校验 |
| Judge 模型 | 和选手同一个模型 | 换更强的独立模型 |
| 相关性粒度 | 0/1 二值 | 0~3 分级（NDCG 才能发挥全部威力） |
| 成本 | 每题 2 次 LLM 调用 | 并发 + 缓存；`evaluate()` 现在还检索了两遍 |
| 回归 | 手动跑脚本 | CI 里跑，分数掉了就拦住 PR |
| 对比 | 只有单次结果 | 存历史，两次实验并排 diff |

**最后一条最重要：**

```
单次评估  →  只能告诉你"现在是 0.42"
历史对比  →  能告诉你"改完之后 0.42 → 0.61，这次改对了"
                    │
                    └──► Evaluation 的全部价值在这里
```

```
        造车（第 1~13 课）          装仪表盘（第 14 课）
              │                            │
              ↓                            ↓
        能跑起来                    知道跑得快不快
              │                            │
              └────────────┬───────────────┘
                           ↓
                  能持续、有依据地跑得更快
```
